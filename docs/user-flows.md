# Skills Hub 用户操作流程（v1 草案）

> 本文档基于 `docs/key-conventions.md`（关键约束 C1–C17）与 `docs/data-flow.md`（数据流向图）梳理出**用户实际可执行的操作流程**。
> 目的：作为后续项目重构的功能对标基准——用户只做"决策"（定义期望），落地（投影到目录）由工具在触发点自动完成，物理状态永远可被推导。
> 与 `docs/key-conventions.md`、`docs/data-flow.md` 配套阅读。

---

## 模型一句话

```
config.json ──推导──▶ desired 期望集 ──投影──▶ 物理目录（软链/复制）
     ▲                                            │
     └────────── 体检 / 诊断 diffSync 对账 ◀──────┘
```

所有流程都落在「操作触发 → 同步生效」这条模型上，无常驻 watcher（C10）。

## 概念澄清：用户个人 skill 集 vs 第三方仓库

所有 skill 资产按**归属来源**分两个世界，它决定标签载体与收编行为：

| 维度 | 用户个人 skill 集（自有） | 第三方仓库（外部） |
|---|---|---|
| 本质 | 用户自己工作流、经验的沉淀 | 开放的内容库，随上游更新 |
| 本体所有权 | 自有，用户可随意编辑/版本管理 | 别人的内容，会变，不应被污染 |
| 管理信息归属 | **所有信息维护在一起**：本体 + 标签 + 策略一体 | 管理与本体**分离**（C3），标签另放载体 |
| 标签体系（C14） | 写 SKILL.md frontmatter 顶层 `tags`（随 git 版本化） | **两套标签体系，可分别启用 / 禁用**：<br>① **仓库自带**：读 frontmatter `tags`（上游自带）<br>② **hub 管理**：写仓库内 marketplace.json 或仓库外文件 |
| 判定依据 | 来源 = 自有仓库 / 收编副本 | 来源 = 外部只读关联 / linked=true（C13） |

> 关键：**第三方仓库无论库内有没有标签，用户都可以维护自己的标签**——只是载体不落在库内本体，而是落在仓库内 / 仓库外文件，避免污染上游本体、避免与上游升级冲突。个人 skill 集则本体和标签一体。
>
> 这对应 C3「管理信息与外部本体分离」+ C14「标签落在生态共识位置」：载体选择先判断来源归属（自有 vs 外部），再选 frontmatter / 仓库内 / 仓库外。
>
> **第三方仓库的两套标签体系（可分别启用 / 禁用）**：
> - **仓库自带标签**：读取该库 `SKILL.md` frontmatter 的 `tags`（上游内容自带）。启用后纳入资产库的标签过滤 / 项目关联。
> - **hub 管理标签**：由本工具维护的一套标签，写仓库内独立文件（如 `.claude-plugin/marketplace.json`）或仓库外文件，供用户自行维护。
> 开关**由探测自动决定**：凡能用任何已知形式检出标签（frontmatter `tags`、marketplace.json 等）即显示对应开关并默认开启，否则**隐藏**；可手动取消防用。组合：只读自带 / 只维护 hub / 两套叠加 / 全关。

## 术语表（Glossary）

> 讨论过程中用到的操作类 / 状态类术语，集中维护于此，其他文档引用本节。随讨论持续补充。

| 术语 | 英文/别称 | 含义 |
|---|---|---|
| **资产库** | 个人 skill 集 | 用户个人工作流、经验沉淀的集中存放处；本体即可 git 管理的非隐藏目录 |
| **自有仓库** | repos | 用户自己的 skill 仓库，本体即资产；登记于 `config.repos`，skill 标识为 `name@<仓库 id>` |
| **第三方仓库** | foreignSources | 外部 / 上游的 skill 仓库；默认「只读关联」引用，收编后接管为自有副本 |
| **沉淀** | 沉淀 | 把 skill 内容收录进资产库成为个人资产的动作 |
| **收集** | collect | **沉淀动作**：把 skill **复制进资产库**，源位置保持不变。相当于拿到一份副本 |
| **接管** | 收编 / replace | **接管动作**（在收集之后）：把源位置（如 Agent 目录）的 skill **替换为软链**指向资产库，收敛为单一本体。**与收集是两个独立操作，可分步执行** |
| **收编** | — | 「收集 + 接管」连做的统称（本文档已拆为两步） |
| **归集** | collect（from agents） | 从 Agent 目录把 skill 沉淀（收集）进资产库；归集的来源是各 Agent |
| **导入** | import / importDirs | 把外部目录 / 第三方仓库的 skill 批量引入资产库（可落入某来源命名空间） |
| **只读关联** | linked=true | 不拷贝第三方本体，仅引用发现；本体随上游更新，标签另放载体 |
| **合并确认** | merge confirm | 同名 / 近名 skill 交汇时，并列展示版本号、描述、来源等必要信息，由用户判断保留哪个版本 |
| **期望集** | desired | 某 Agent / 项目由配置推导出的「应装 skill 集合」，运行时计算，**不落盘** |
| **投影** | projection | 将期望集落到物理目录（软链 / 复制）的过程 |
| **同步** | sync | 以「期望 vs 物理」对账（diff）为驱动的投影动作；缺则建、多则删、diff 空则不动 |
| **活跃 Agent** | activeAgents | 用户在 UI 配置的实时同步作用域集合；期望 / 标签变更只自动作用于其成员 |
| **载体** | tag carrier | 标签存放位置：SKILL.md frontmatter / 仓库内文件 / 仓库外文件，按来源归属选择 |
| **仓库自带标签** | upstream tags | 读第三方仓库 `SKILL.md` frontmatter 的 `tags`（上游内容自带）；可单独启用 / 禁用 |
| **hub 管理标签** | hub tags | 由本工具维护的一套标签，写仓库内文件（如 `.claude-plugin/marketplace.json`）或仓库外文件；可单独启用 / 禁用，供用户自行维护两项标签体系 |

## 流程一：上手起步 · 初次进入建库

> 目标：形成一份可用的「用户个人 skill 集」（即资产库）。
> 首次进入走**引导式建库向导**：先判定用户现状（有无现成资产），再分流到 A（导入现有）或 B（从 Agent 归集）。

### 流程一 · 引导：初次进入建库向导

| 步骤 | 用户操作 | 工具判断 / 响应 |
|---|---|---|
| 0.1 | 进入首启向导 | 提问「是否已有现成的个人 skill 资产库？」 |
| 0.2 | **有** → 走流程一-A；**无** → 走流程一-B | 分支路由 |
| 0.3 | 配置仓库路径（**新空目录** 或 **已有目录**） | 落库 `repos[]`（C5：用户决策） |
| 0.4 | 探测/确认 Agent，必要时覆盖自定义目录 | 内置清单 + 用户覆盖（AG-04/05） |
| 0.5 | 设置「活跃 Agent 集合」 | 记 `activeAgents`（C5） |
| 0.6 | 完成向导 → 进入资产库首页 | 按分支落地（A/B） |

### 流程一-A · 导入已有的个人资产库

> 适用：用户已有现成的个人 skill 资产库（本地目录 / git 仓库）。指向后**实时纳入**管理，**不收集、不接管、不复制、不移动**——本体即已在位。

| 步骤 | 用户操作 | 工具响应（依据约束） |
|---|---|---|
| A1 | 指向一个已有 skill 资产库目录 / 仓库 | `scanAll` 按其布局实时扫描发现 skill 本体（C4/C15） |
| A2 | —（无需额外动作） | 直接纳入资产库视图；库内重名已按 `name` 归一化收敛，不存在多副本（C9） |
| A3 | 打标签补全（"未打标签"过滤） | 自有 → 写 SKILL.md frontmatter（C3/C14） |

> 流程 A 本身就是用户资产库本体，故**不涉及「收集 / 接管」**（那不适用于"自己的库"）；「收集/接管」仅发生在从 Agent 目录归集、或从第三方仓库汇入（见流程一-B、流程二-C）。

### 流程一-B · 用 Agent 中的 skill 归集出资产库

> 适用：用户**没有现成资产库**。目标库可为**新空目录**（归集出内容），也可是**已有内容的现存库**（在此之上补充）。从各 Agent 目录筛选沉淀 skill。

| 步骤 | 用户操作 | 工具响应（依据约束） |
|---|---|---|
| B1 | 指定目标资产库目录（空目录 或 现存库） | 落库 `repos[]`；空库则自动初始化（C5） |
| B2 | 触发「扫描归集」(`collect`) | `scanAll` 扫描 Agent 目录，列出候选 skill（C4，不落快照） |
| B3 | **挑选**要沉淀的 skill | **收集**=复制入仓；命中与库内或其他 Agent 同名 → 进入**合并确认** |
| B3a | **合并确认**：同名/近名候选对比 → 决定保留哪个版本 | 并列展示各候选的 **版本号 / 描述 / 来源**等必要信息；用户判断保留（IM-02/C9）；未保留归入其他来源命名空间或丢弃 |
| B4 | （可选）**接管**：原 Agent 目录的 skill 替换为软链 → 资产库 | replace 语义（IM-03）；**收集与接管是两个独立操作，可分步执行**（C11/C13） |
| B5 | 打标签补全（"未打标签"过滤） | 自有 → 写 SKILL.md frontmatter（C3/C14） |

> 边界：归集只动「自有 / 收集 / 接管」目录；外部只读与 Agent 自带技能不碰（C13）。
> 现存库走 B 时，B3a 的合并确认即起到"并入不覆盖、冲突先确认"的作用。

### 流程一 · 已确认决策
- **「收集」与「接管」是两个独立操作**：收集把 skill 内容复制进资产库（沉淀），源位置保持不变；接管再把源位置（Agent 目录）替换为软链指向资产库。默认先「收集」，是否「接管」由用户按需决定。（对应 data-flow G4 定稿）
- **合并确认**：任何同名 / 近名 skill 交汇（导入、归集、批量导入）都必须并列展示**版本号 / 描述 / 来源**等必要信息，由用户判断保留哪个版本（对应 IM-02）。
- **初次进入走「引导式建库向导」**：先问"有无现成资产"，再分流 A / B（统一此前两条路径的进入方式）。

## 流程二：资产入库与补充（先于打标签 / preset）

> 把散落的 skill 收进资产库、充实资产库，**全部发生在打标签 / 维护 preset 之前**——先让资产就位，再谈资产管理。
> 含三类来源：从 Agent 归集补充、导入第三方仓库（只读关联）、把第三方内容复制入库。

### 流程二-A · 从 Agent 归集补充

> 若流程一-B 未归集完，或之后想再吸收某 Agent 的 skill。步骤同流程一-B（B1–B5），此处不再展开。

### 流程二-B · 导入第三方仓库（登记 + 只读关联）

> 处理**第三方仓库**：开放内容库，随上游更新。登记进管理、实时纳入发现，**不拷贝、不污染库内本体**（C3/C13）。

| 步骤 | 用户操作 | 工具响应（依据约束） |
|---|---|---|
| B1 | 登记第三方仓库（目录路径 / git 地址），选布局 | 落库 `foreignSources[]`；`flat / nested / auto` 识别（C15 / EK-01） |
| B2 | 选择关联方式：**只读关联**（默认） | `linked=true`：不拷贝本体，仅引用发现（EK-03 / C13） |
| B3 | — | **自动探测**可识别标签，可用体系开关**默认开启**、无法检出的**隐藏**：<br>检出 frontmatter `tags` → 「仓库自带」显示<br>检出 marketplace.json / 仓库外文件 → 「hub 管理」显示<br>皆未检出 → 全部隐藏 |
| B4 | — | `scanAll` 实时发现库内 skills 及已开启体系的标签；归属该第三方「来源命名空间」 |
| B5 | 浏览 / 过滤库内 skill；如需，在显示出的体系上打 / 改标签 | 自带标签按启用读取；hub 标签写仓库内/外文件（C14） |
| B6 | （可选）把库内 skill 并入个人资产库 | 走流程二-C 收集入库 |

> 边界：B 全程不改写第三方仓库；对第三方仓库**不适用「接管」**（接管只作用于自有 / Agent 目录）——语义见术语表。

### 流程二-C · 将第三方仓库内容导入个人资产库（收集入库）

> 挑中第三方 skill，**收集（复制）进个人资产库**，形成「自有收藏」副本，此后可独立维护。来源是已关联的第三方仓库。

| 步骤 | 用户操作 | 工具响应（依据约束） |
|---|---|---|
| C1 | 在第三方仓库资产视图**挑选**要沉淀的 skill | 列出候选（基于流程二-B 的扫描视图） |
| C2 | 触发「收集入库」 | **复制**进个人资产库的某来源命名空间；同名去重（C9） |
| C3 | 命中与资产库已有 skill 同名 / 近名 | 进入**合并确认**：并列展示版本号 / 描述 / 来源，由用户决定保留哪个（IM-02/C9） |
| C4 | （可选）打标签、纳入 preset | 已入库副本归「自有」，标签写 SKILL.md frontmatter（C3/C14） |

> 区别：流程二-B 是"登记 + 关联"，本体留在第三方；流程二-C 是"复制入库"形成自有副本。**对第三方仓库只做 C 的收集，不做接管**——第三方仓库保留原样，入库副本以链接/归档方式与来源关联。
> 合并确认沿用流程一-B B3a 的同一交互与判据（见流程讨论点 2）。

## 流程三：资产管理 · 打标签 / preset / 分发（资产就位后）

> 最重要的链路（data-flow §4.2）。资产已入库就位，此后用户只做"决策"，其余全靠触发。

| 入口 | 用户操作 | 自动作用域 |
|---|---|---|
| **浏览/打标签** | 资产库搜索过滤 → 打标签 / 编辑 skill | 标签变更触发 |
| **维护 preset** | 创建/编辑/删除集合内 skill、激活/取消 | 触发分发到活跃 Agents |
| **Agent 手动精确控** | 对某 Agent 开/关某 skill（explicitOn/Off） | 该 Agent |
| **切换 Agent** | 加入 / 移出活跃集合 | 加入即就位、移出即回退（AA-04） |
| **手动兜底** | 点「立即生效」 | 单 Agent 全量对账 |

### 流程三-A・浏览资产库与打标签（细化）

> 浏览 = 检索 + 过滤 + 看清来源归属；打标签 = 把**用户自己的语义编码到资产上**，作为投放 / 项目关联的输入（C6/C14）。

**① 浏览 / 过滤维度**

| 方式 | 说明 |
|---|---|
| 名称 / 全文搜索 | 按 skill 名称、描述模糊检索 |
| 按标签过滤 | 选标签筛出对应 skill；支持多标签（且 / 或） |
| 按来源过滤 | 自有 vs 第三方（可往下钻到具体来源命名空间） |
| 未打标签过滤 | 一键列出无标签资产，用于"补全" |
| 状态视图 | 激活 / 未激活、当前已分发到哪些 Agent、被哪些 preset 引用 |
| 查看详情 | 版本号、描述、来源、标签（含仓库自带的标签）、当前归属（自有 / 第三方） |

**② 打标签**

| 场景 | 标签载体（C3/C14） | 用户操作 | 触发效果 |
|---|---|---|---|
| 自有 skill | `SKILL.md` frontmatter `tags` | 直接编辑 | 标签变更 → 重算项目关联（§4.3）与投放 |
| 第三方（两套体系） | 探测出的体系：仓库自带（读）/ hub 管理（写仓库内或仓库外文件） | 在显示的体系上打标；不经探测的体系隐藏不可打 | 同上 |
| 批量打标 | 按每项来源选载体 | 多选 skill → 一次打 / 删同一批标签 | 逐项触发变更 |

**③ 标签元操作**

- 打 / 删 / 改某个 skill 的标签（依赖载体：自有写 frontmatter，第三方写 hub 载体）
- **全局重命名标签**：所有承载该标签的载体同步改名
- **合并标签**：把两个标签归并成一个
- **补全清单**：基于"未打标签过滤"逐个补齐
- **一致性检查**：同 skill 多载体标签漂移告警并就地比对（对应 G1 建议新增检查项）

关键规则：
- 载体选择**先判来源归属、再选载体**（概念澄清表）。
- 标签即投放策略 / 关联输入，**改动立即重算期望集与关联**（C6/C7），全程幂等。
- 第三方标签**不落库内本体**，避免污染上游（C3/C14）。

### 流程三-B · 维护 preset（细化）

> preset = **命名 skill 集合 + 绑定目标 Agent（或 Agent 集合）+ 激活状态**。成员按 skillMeta 引用 + 分发策略组织，**不复制本体**（C6/C8）；资产就位后编辑 preset 即触发分发。打标签（三-A）是这里按标签批量装配的前提。

| 步骤 | 用户操作 | 工具响应（依据约束） |
|---|---|---|
| P1 创建 | 新建 preset：命名 → 挑成员 skill（逐个挑 / 按标签批量 / 复用已有 preset）→ 绑定目标 Agent | 记 `presets[]`（决策，C5）；成员 = `skillMeta` 引用（C8） |
| P2 激活 | 激活该 preset | 并入目标 Agent 期望集；对**活跃** Agent 触发分发（AA-02/03） |
| P3 编辑增删 | 在 preset 内加 / 移 skill | 增量触发分发到绑定 Agent（C7 幂等） |
| P4 调整绑定 | 更换 / 解散绑定 Agent | 旧 Agent 回退、新 Agent 投影（AA-04） |
| P5 取消激活 | 停用 / 关闭该 preset | 移出期望集并触发回退；**成员与集合保留**，可再次激活 |
| P6 复用组织 | 复制成新 preset、跨 Agent 复用、按标签重组 | 沿用 skillMeta 与分发策略 |
| P7 手动兜底 | 点「立即生效」 | 单 Agent / 全局全量对账 |

关键保障（preset 视角）：
- **激活状态是决策（C5）**；成员增删、绑定变更都是触发点，即时投影。
- 只在**活跃集合**上立即生效，非活跃懒同步（C12 / AA-03）。
- 成员按引用不复制；分发时才投影软链（C6/C8），全程幂等（C7）。

### 流程三-C · Agent 管理（细化）

> 每个 Agent 有独立覆盖（globalDir / 同步方式 / 管理模式 / 显式开关），并隶属活跃集合。管理者只做决策，投影即触发。

| 步骤 | 用户操作 | 工具响应（依据约束） |
|---|---|---|
| N1 探测 / 配置 | 扫描 Agent；对单 Agent 覆盖 `globalDir`、同步方式（软链 / 复制）、归属目录 | 内置清单 + 用户覆盖（AG-04/05）；记 `agents`（C5） |
| N2 管理模式 | 选 `preset` 模式（绑定某 preset）或 `manual` 模式（全靠显式开关） | 决定该 Agent 期望集基准（基准：preset / 标签命中 ∪ explicitOn − explicitOff，C6） |
| N3 手动精确控 | 对某 Agent 显式开 / 关某 skill | 记 `explicitOn / explicitOff`（C5）；重算该 Agent 期望集并增量分发（C7） |
| N4 设活跃 | 将 Agent 加入 `activeAgents` | **加入即就位**：立即对账并投产（AA-04 / G6）；之后纳入自动同步作用域 |
| N5 取消活跃 | 将 Agent 移出 `activeAgents` | **移出即回退**：按策略回退到未投产状态（AA-04）；恢复懒同步（C12 / AA-03） |
| N6 立即生效 | 进某 Agent 详情页点「立即生效」 | 单 Agent 全量对账（C12） |
| N7 生命周期 | 启 / 停 / 移除某 Agent 登记 | 停用保留配置可再启；移除清登记与已投产软链 |

**Agent 视图（详情体检）**
- 期望集（基准 ∪ explicitOn − explicitOff）与当前物理投放 diff
- 显式覆盖清单（explicitOn / explicitOff）
- 同步方式、管理模式、所属 preset、是否活跃
- 软链 / 副本健康、失效项（并入流程五体检）

关键保障（Agent 视角）：
- **自动同步只作用于活跃集合**，非活跃懒同步，不得静默扩散（C12 / AA-03）。
- `explicitOn / explicitOff` 配置层统一存 `name@source`，仅投影层归一化（G2 待定稿）。
- 期望集为**运行时计算结果，不落盘**（C6）；全程幂等（C7）。

## 流程四：项目协作 · 一套本体、多 Agent 共享（细化）

> 项目把"本体"沉淀进 `.agents/skills`（复制、可提交 git），其余 Agent 项目目录软链到 `.agents`。投放对象以目录结构为事实。期望 = 标签命中 ∪ explicitOn − explicitOff（§4.3）。

| 步骤 | 用户操作 | 工具响应（依据约束） |
|---|---|---|
| J1 登记 / 创建项目 | 添加项目路径、命名 | 记 `projects[]`：`path / tags[] / explicitOn[] / explicitOff[]`（C5） |
| J2 打标签 / 显式覆盖 | 编辑项目 `tags`；可选对某 skill 设 explicitOn / explicitOff | 标签命中进期望集基准；explicit 为手动覆盖（C6） |
| J3 算期望集 | — | 期望 = 标签命中 ∪ explicitOn − explicitOff，**运行时计算，不落盘**（C6） |
| J4 同步到本项目 | 点「同步」 | `syncProject`：`.agents/skills/` **复制本体**（PJ-02，可提交 git）+ 各 Agent 项目级目录软链 → `.agents`（PJ-03） |
| J5 投放对象 | 决定需投放的 Agent | **以目录结构为事实**：`<project>/.<agent>/skills` 软链存在与否即投放事实，**不写 config**（§4.3） |
| J6 变更重投 | 改 tags / explicit 之后 | 沿用当前已投放 Agent 集合重投（§4.3） |
| J7 回写仓库 | 点「push 回仓库」 | `.agents → 仓库` 双向同步（PJ-05，**未实现** data-flow G3） |
| J8 移除 / 解绑 | 关闭某项目级投放、删除项目登记 | 解除软链、清登记；`.agents` 本体保留与否按需 |

**项目视图（详情体检）**
- 期望集 vs 物理投放 diff
- 标签命中明细、显式覆盖清单
- 已投放的 Agent 及项目级软链健康
- 是否已提交 git / 有待回写项（对应 G3）

关键规则：
- **标签 = 投放策略而非快照**；改动沿用已投放 Agent 集合重投（§4.3，C6/C7）。
- `.agents/skills` 是项目唯一可提交 git 的本体副本（PJ-02）；Agent 项目级目录均软链到它（PJ-03）。
- 投放范围以目录结构为唯一事实，不落入 config（避免双事实漂移，C13）。

## 讨论点（梳理过程中浮现的决策分叉）

1. **"首启建库"与"日常流水"的衔接**：引导建库已完成首启 A/B 分流，但用户视角里"从扫描到用上"往往是连续动作——A/B 完成后是否直接引导到"激活 preset / 设活跃 Agent"？（对应 flow §4.1→§4.2 的衔接体验）
2. **合并确认（B3a）的判据来源**：版本号 / 描述从哪读——统一要求 SKILL.md frontmatter 带 `version` 字段，还是从 git 历史 / 文件差异推导？无版本号时如何并列展示？
3. **用户的"决策"到底列哪些**：C5 已列 repos / agents / presets / projects / activeAgents / skillMeta。本版流程里新增的"操作"是否都落在六类决策之内，还是出现了"物理结果被误当决策"的越界？
4. **手动兜底的层级**：流程二中放了「手动立即生效」（单 Agent 全量）和「手动同步按钮」（复制模式）两类——是否需要区分，还是统一成一个"对账"动作？
